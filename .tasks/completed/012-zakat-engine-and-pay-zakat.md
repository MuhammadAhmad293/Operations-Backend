  - **Design decisions worked out now, ahead of the sub-tasks that need them** (documented here so the reasoning survives context, per this session's established practice — will be reconfirmed against live data as each lands):
    - **Pot computation for `GOLD`-currency wallets must use `PureGoldGrams`, not raw `Amount`** (sub-task 2). The plan's sub-task-2 row says "reuses the Wallet balance helper," which sums raw `Amount` — but BR-03 is explicit and repeated: *"The wallet screen displays the RAW purchased grams... Zakat calculations always use the pure 24K equivalent."* Raw grams and pure grams are two different, deliberately-distinguished numbers in this system; reusing the raw-balance helper unmodified for a `GOLD` wallet would silently ignore karat and overstate the pot for anyone holding sub-24K gold. Read the plan's phrasing as "reuse the *pattern*," not "reuse the *exact query*," since BR-03's rule is unambiguous and takes precedence. Cash/`SILVER` wallets (silver has no karat per spec) *do* use the plain balance helper, converted via `IRateService.GetLatestAsync(currency, "GOLD")`.
    - **A cross-currency transfer's credit into a `GOLD` wallet is already pure-gold-equivalent, no gap to fix.** `Transaction.PureGoldGrams` is only ever computed from the *source* wallet's currency (`ValidateAndResolveAsync` line ~331), so a transfer *into* a gold wallet from a non-gold wallet has `PureGoldGrams = null` on that credit — it looked like a real gap at first. It isn't: the credited `ConvertedAmount` is computed via `IRateService.GetLatestAsync(sourceCurrency, "GOLD")`, and that rate is itself the pure-24K market price (Frankfurter's `XAU` quote, per Phase 010) — so `ConvertedAmount` for a transfer-in credit already *is* the pure-gram figure by construction, just stored in a different field. Sub-task 2's pot computation will treat a `GOLD` wallet's transfer-in credits (`ConvertedAmount ?? Amount`) as pure grams directly, alongside `PureGoldGrams` for every other transaction type touching that wallet — mirroring `GetSignedSumForWalletAsync`'s existing FROM/TO split, just swapping which field the FROM-side reads. The one genuinely unresolved micro-edge-case — a same-currency `GOLD→GOLD` transfer, where neither `PureGoldGrams` nor `ConvertedAmount` is set on the credit (only raw `Amount`) — is rare enough (transferring gold between two of the user's own gold wallets) that it's treated as an accepted known limitation (falls back to raw `Amount`, i.e. assumes the transferred grams are pure), not fixed, since fixing it would mean touching Phase 009's already-shipped `TransactionService` for a scenario the plan never mentions.
    - **`ZakatService.Pay`'s expense transaction will be built directly in `ZakatService`, not via `ITransactionService.Add`** (sub-task 6), despite the plan's "creates the expense transaction via the Phase-009 creation path" wording. Reason: the plan requires the audit `ExchangeRate`/`ConvertedAmount` pair to be stored on this transaction (base-currency amount → wallet-currency amount), but `TransactionService.ResolveConversion` unconditionally discards any caller-supplied rate/converted-amount whenever `toWallet is null` — true for every Expense, since a Zakat payment has no destination wallet. Reusing `Add` as-is would silently null out exactly the fields this feature needs. A Zakat payment's shape is also considerably simpler than the general case (fixed category, no transfer, no fee, no user-facing karat choice — always defaults to 24 per the plan), so direct construction avoids either (a) modifying Phase 009's shared `ValidateAndResolveAsync`/`ResolveConversion` for every future Expense/Income just to special-case this one caller, or (b) exposing an internal Zakat-only overload on the public `CreateTransactionDto`. `ZakatEngine.ReevaluateAsync` **will** still be called from `ZakatService.Pay`'s own `ExecuteInTransactionAsync` block (mirroring `TransactionService.Add`'s pattern exactly), so hawl re-evaluation isn't lost by skipping the shared path — only the validation/resolution plumbing is skipped, not the required side effects.
    - **Confirmed, not re-implemented**: `TransactionService.Update`/`Delete` already call `ZakatEngine.RecomputeCyclePaymentAsync(transaction.ZakatCycleId)` when a Zakat-linked transaction is edited or deleted (visible in the already-shipped Phase 009 code) — Phase 009 was built with this forward hook in place. This means sub-task 11's "delete a linked expense → reverts to Due" verification requires zero changes to `TransactionService`; it'll work automatically once `RecomputeCyclePaymentAsync` (sub-task 4) has a real implementation. **One residual gap noted, not fixed**: `Update` does *not* recompute `ZakatGoldGrams` if a user edits a Zakat-linked transaction's `Amount` — the stored gram figure would go stale relative to the new amount. Out of scope here (the plan's sub-task list never mentions touching `Update`), flagged for a future phase if it matters in practice — editing a completed Zakat payment's amount is an unusual, not a primary, flow.

- Sub-task 3 (2026-08-08): implemented the real `ZakatEngine.ReevaluateAsync` (`Meezan.Services/ZakatEngine/ZakatEngine.cs`, replacing the Phase 009 no-op stub), injecting `IUnitOfWork`/`IZakatPotCalculator`/`IHijriCalendarHelper`. Logic: no Active cycle + pot≥85g → create one (`HawlStartHijri`=today's Hijri, `HawlDueHijri`=+1 Hijri year); Active + pot<nisab → Broken (only that cycle, `return`s immediately — never falls through to the due-check); Active + pot≥nisab → a **loop** (not a single `if`) `while (today >= activeCycle.HawlDueHijri)`: transition to Due (`PotGoldGramsAtDue`/`ZakatDueGoldGrams` = pot / pot×2.5%, valued at this call's single pot figure) and unconditionally start a new Active cycle dated from the *old* cycle's `HawlDueHijri` (not "today" — keeps the Hijri calendar exact regardless of how late the re-evaluation happens to run), continuing the loop against the new cycle so a multi-year gap since the last evaluation self-heals into the correct number of cascaded Due cycles rather than just one. Hijri date comparisons use `string.CompareOrdinal` on the already-established sortable `yyyy-MM-dd` Hijri format (Phase 009's `HijriCalendarHelper` convention — no parsing). `RecomputeCyclePaymentAsync` remains a stub (sub-task 4). `dotnet build Meezan.sln` clean, 0 errors.
  - **Live-verification caught a real, significant bug**: the very first test (fund a wallet to `~117g` pot, well past the `85g` nisab) created **no cycle at all**. Traced via the EF Core SQL command log: `ReevaluateAsync` runs *inside* `TransactionService.Add`'s `ExecuteInTransactionAsync` delegate, immediately after `Create(transaction)` stages the pending insert — but EF Core does **not** auto-flush pending changes before a fresh LINQ query, so `ComputePotGoldGramsAsync`'s wallet-balance query was reading the wallet's balance **as it stood before** the very transaction that was supposed to push it over nisab. This meant the hawl state machine could never correctly detect the *exact* transaction that crosses the nisab threshold — a core-functionality bug, not an edge case. **Fixed inside `ZakatEngine.ReevaluateAsync` itself** (no need to touch Phase 009's already-shipped `TransactionService`): calls `UnitOfWork.CommitAsync()` (`SaveChangesAsync`, not a DB-transaction commit) as its very first line, flushing any pending changes from the caller into the *same ambient SQL transaction* before reading anything — visible to this method's own queries via read-your-own-writes, while `ExecuteInTransactionAsync`'s outer transaction still commits/rolls back atomically at the end exactly as before. This same flush-first fix will be needed in `RecomputeCyclePaymentAsync` (sub-task 4) for the identical reason.
  - **Full state-machine re-verification after the fix**, all via real HTTP transactions against a live wallet (no mocking), with `HawlDueHijri` manipulated directly via SQL between steps to simulate elapsed time (the only practical way to test a year-long hawl without waiting a year): (1) pot crossing `85g` → `Active` cycle created, `HawlDueHijri` = exactly `+1 Hijri year` from `HawlStartHijri`; (2) backdating `HawlDueHijri` to today + one more transaction → cycle 1 → `Due` with `ZakatDueGoldGrams` = exactly `2.5%` of the recorded `PotGoldGramsAtDue` (`116.954 → 2.924`), **and** a new Active cycle 2 created starting exactly at cycle 1's old `HawlDueHijri`; (3) repeating the backdate-and-trigger pattern → **two simultaneous Due cycles** (1 and 2, cycle 1 provably untouched by cycle 2's transition) **plus** a fresh Active cycle 3 — exactly the plan's "two consecutive years unpaid" scenario; (4) draining the wallet below nisab → cycle 3 → `Broken`, cycles 1/2 (Due) completely untouched, confirming Broken only ever affects the current Active cycle; (5) funding back above nisab → a **brand-new** cycle 4 created (the Broken cycle 3 is never resumed/reused). Every field matched hand-calculated expectations at every step. Deleted all test data afterward.
