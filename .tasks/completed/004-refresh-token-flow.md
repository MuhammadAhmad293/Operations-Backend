# 004 – Refresh Token Flow

## Status

`completed`

## Goal

Add a full refresh-token flow (multi-device sessions, rotation with reuse detection, absolute session lifetime, concurrency-safe rotation, revocation audit trail, configurable cookie policy, device cap, scheduled cleanup) so the JWT access token can go back to being short-lived (15 min) without forcing frequent re-logins, supporting both the Angular web client (HttpOnly cookie) and future mobile clients (JSON body).

## Context

Today `AuthService.Login` issues only a JWT access token — no refresh token exists — and `JwtSettings.ExpiryMinutes` has drifted to 60 in `appsettings.json` (from an originally-intended 15) as a workaround for the missing refresh flow. This task restores a short-lived access token safely by adding refresh tokens, while satisfying the following non-negotiable security requirements set by the user:

1. Web-vs-mobile delivery (cookie vs JSON body) must be decided by server-side routing (separate endpoints), never by a client-supplied header — a header is attacker-controlled and must not gate security behavior.
2. Multi-device sessions: logging in on one device must not invalidate another device's session.
3. Refresh token rotation with reuse detection: a revoked/used token presented again must revoke its entire rotation chain (`FamilyId`), not the user's other devices.
4. Absolute session lifetime on top of the sliding refresh expiry.
5. The rotation step (revoke old + create new) must run inside an explicit database transaction with optimistic concurrency protection (`rowversion`) so two concurrent refresh calls can't corrupt state.
6. Full revocation audit trail (`RevokedReason`), configurable cookie policy, a configurable max-active-devices cap, and scheduled cleanup of old rows.

Full design detail (entity shape, exact service-method logic, controller routes, settings shape) lives in the approved plan at `C:\Users\lenovo\.claude\plans\add-authorize-feature-to-glittery-lark.md` — this task file tracks execution against that plan one sub-task at a time, per `.results/TASK_PLANNING_AND_WORKFLOW.md`.

- All 9 sub-tasks now complete. Ran the app live (`dotnet run --no-launch-profile`, local SQL Server + RabbitMQ both reachable) and exercised the flow end-to-end, which caught and fixed 3 real bugs the build alone couldn't surface:
  1. `LoginDto`/`RefreshTokenRequestDto`'s `DeviceId`/`DeviceName`/`Platform` were non-nullable reference types, so `[ApiController]`'s implicit model validation rejected any request that omitted them (400 "field is required") — changed to `string?`, and correspondingly loosened `IAuthService`/`AuthService`'s `ipAddress`/`deviceId`/`deviceName`/`platform` parameters to nullable throughout.
  2. `RefreshToken.DeviceId`/`DeviceName`/`Platform`/`CreatedByIp`/`LastUsedIp` were non-nullable in the entity, so EF generated `NOT NULL` columns — any login/refresh that legitimately omits device metadata (e.g. `web/login`, which never collects a `DeviceId`) threw `DbUpdateException` on save. Fixed via a second migration, `MakeRefreshTokenMetadataNullable`, relaxing all 5 columns to nullable (generated and applied).
  3. `RefreshTokenSettings.Cookie.Path` defaulted to `/api/auth` (lowercase) but the real route is `/api/Auth` (capital A, from `AuthController`'s class name via `[Route("api/[controller]")]`) — cookie path matching is case-sensitive in real browsers (and in curl), so the cookie was silently never sent back on `web/refresh-token`/`web/logout`, both returning "Invalid request". Fixed the default in both `RefreshTokenSettings.cs` and `appsettings.json` to `/api/Auth`.
