- Sub-task 1 (2026-08-08): created `OverviewDto` (`Meezan.Dto/DTOs/Overview/` — `{Income, Expense, Total}`), `CalendarDayDto`/`CalendarDto` (`Meezan.Dto/DTOs/Calendar/` — `{Days: List<CalendarDayDto>, MonthIncome, MonthExpense, MonthTotal}`, one `Days` entry per calendar day of the month including zero-activity days, so the frontend can render a full grid), `StatisticsDto`/`StructureCategoryDto`/`StructureDto` (`Meezan.Dto/DTOs/Statistics/` — `StatisticsDto` embeds an `OverviewDto` per UC-20's "opening balance, ending balance..., overview block"). **No Mapster mapper added** — all four DTOs are hand-assembled aggregates with no single source entity to map from (same reasoning as Phase 009's `TransactionGroupDto`, which also has no dedicated mapper); `Category.Kind`'s enum→string conversion for `StructureDto.Kind` will just be a plain `.ToString()` in the service, not a registered Mapster config.
  - **Design decisions made now, ahead of sub-tasks 2–4, since they shape these DTOs' fields** (documented here so the reasoning isn't lost, will be reconfirmed against test data as each service lands):
    - **Currency**: neither BR-11 (Overview math) nor UC-19/20 states a currency for the aggregate figures, but every other account-wide aggregate in the spec (BR-12 total balance, BR-13 Zakat pot) explicitly converts to a common unit — so `Income`/`Expense`/`Total`/`OpeningBalance`/`EndingBalance`/`Amount` will all be converted to the account's **base currency** at the latest rate, mirroring `AccountService.ComputeTotalBalanceAsync`'s exact per-wallet `IRateService.GetLatestAsync` pattern. No `BaseCurrencyCode` field was added to these DTOs — the frontend already has it from `GET /api/account` (whose own `AccountDto` doesn't repeat it either... it *is* the source), so repeating it here would be redundant.
    - **`ExcludeFromTotal` scope**: BR-04's literal text lists only "the account total balance AND the Zakat pot" as what the flag affects. Overview/Calendar/Structure are transaction-*flow* views (income/expense over a period), not balance snapshots, so they will include **every** wallet's transactions regardless of the flag — only `StatisticsDto.OpeningBalance`/`EndingBalance` (genuine balance snapshots, and literally what BR-04's "statistics ending-balance note" refers to by name) will exclude flagged wallets.
    - **Transfers/Fees**: Transfers move money between the account's own wallets — no external income/expense — so they're excluded from `Income`/`Expense`/`Total` math entirely (only `TransactionType.Income`/`Expense` count). Fee transactions are `Type = Expense` (Phase 009 convention) and BR-09 explicitly says fees "appear independently in overviews/statistics," so they count as ordinary expenses with no special-casing needed.

  - **`GetStatistics`**: `OpeningBalance`/`EndingBalance` are BR-12's total-balance formula (non-`ExcludeFromTotal` wallets only, matching `AccountService`'s existing `GetByAccountAsync`-based precedent — soft-deleted wallets are excluded from balance sums entirely, same as the live `/api/account` total) evaluated at two cutoff dates: opening uses `periodStart - 1 day` (or `DateOnly.MinValue` when the period is "all," which — since no real transaction can predate it — elegantly reduces to "just the wallets' `InitialAmount`s," exactly what "opening balance of all time" means, with no special-case branch needed); ending uses `periodEnd` (or unbounded/current when null, i.e. "all"/today). `ExcludedNote` is non-null whenever at least one wallet is `ExcludeFromTotal`. `Overview` is composed by calling `IOverviewService.GetOverview` for the same period rather than recomputing — a small, accepted duplicate account-fetch in exchange for a clean interface-based dependency (no need for the concrete-type-injection trick `RateService`/`FrankfurterRateProvider` uses, since `IOverviewService`'s public contract already provides everything needed here).
