# 016 – Rate Fallback Bug + In-Use Currency Sync Enhancement

## Status

`completed`

## Goal

Fix the reported SAR↔GOLD rate-resolution failure when Redis is down and only USD-anchored
snapshots exist, then extend the sync job to fetch direct pairs for currencies actually in use
so common conversions no longer depend on derivation at all.

## Context

Reported 2026-08-14: with base currency SAR and Redis down, adding a transaction against a GOLD
wallet failed to resolve a rate even though USD-anchored RateSnapshots (USD→SAR, GOLD→USD) were
present. The approved design (plan Phase 010 sub-task 7, `.tasks/completed/010-rate-integration-architecture.md`)
specifies direct → inverse → cross-through-USD resolution in `RateService.GetLatestAsync`, with
Redis failures degrading transparently to the DB. Covers BR-19.

## Sub-Tasks

| #   | Description                                                                                                       | Status  |
| --- | ------------------------------------------------------------------------------------------------------------------ | ------- |
| 1   | Diagnose `GetLatestAsync`'s cross-through-USD/DB-fallback path; fix if broken; add regression unit tests (direct/inverse/cross for EGP→SAR and SAR→GOLD, DB path, cache bypassed and cache genuinely throwing) | ✅ done |
| 2   | Sync job: fetch direct pairs for currencies actually in use (account base currencies + non-deleted wallet currencies) against each other and against GOLD/SILVER, batched, append-only | ✅ done |
| 3   | Wallet creation: when the wallet's currency has no recent snapshot, enqueue a background sync job for it (no inline provider call — BR-19) | ✅ done |
| 4   | Resilience + end-to-end verification matrix (Redis stopped: SAR base + GOLD wallet transaction succeeds; post-enhancement: direct SAR→GOLD snapshots exist; new-currency wallet triggers DB+Redis population without an inline provider call) | ✅ done |

## Notes

- Sub-task 1 (2026-08-14): Read `RateService.GetLatestAsync` (`Meezan.Services/RateService/RateService.cs:149`) end to end. It already does exactly the approved algorithm: same-currency shortcut, then `ResolveDirectOrInverseAsync(from, to)` (direct snapshot, else `1/inverse`), and — when neither side is USD — cross-through-USD by resolving `from→USD` and `USD→to` through that *same* direct-or-inverse helper and multiplying. Each of those lookups goes through `GetStoredRateAsync`, which tries Redis via `TryCacheGetAsync` (catches any exception, logs a warning, returns `null`) and then falls back to `RateSnapshotRepository.GetLatestByPairAsync` — so the cross-through-USD path **is** reached from the DB-fallback branch, not just the cache-hit branch. `RatesUnavailableException` is only thrown when no combination of stored snapshots resolves the pair, and `ErrorHandlingMiddleware` maps it to 503, not 500; `UnitOfWork.ExecuteInTransactionAsync`'s catch-block only rolls back and rethrows unchanged, so the exception type survives to the middleware. No code defect found in this path.
  - Proved this empirically rather than trusting the read: added `ThrowingDistributedCache` (`Meezan.Tests/TestSupport/ThrowingDistributedCache.cs`) — every operation throws, simulating a genuinely-down Redis (the old, already-fixed bug class from Phase 010 sub-task 7 was an *unhandled* Redis exception; this fake would have caught that regression immediately). Gave `RateServiceTestFixture` an optional `IDistributedCache` constructor parameter (defaults to the existing `FakeDistributedCache`) so tests can choose which cache behavior to exercise. Added `RateResolutionTests.cs` (`Meezan.Tests/RateIntegration/`) seeding only USD-anchored `RateSnapshot` rows (`USD→SAR=3.75`, `USD→EGP=49.78`, `GOLD→USD=136.81`/gram, `SILVER→USD=2.0`/gram — never the pair or its inverse directly) and asserting `GetLatestAsync` resolves direct (`USD→SAR`), inverse (`SAR→USD`), cross-fiat-fiat (`EGP→SAR`), and cross-fiat-metal (`SAR→GOLD`, the exact reported scenario) correctly — each as an `[InlineData(false)]`/`[InlineData(true)]` theory run once against the empty `FakeDistributedCache` (cache-miss→DB) and once against `ThrowingDistributedCache` (cache-down→DB), asserting identical results both times. Also covers the true-negative case (`SAR→ZZZ` correctly throws `RatesUnavailableException`). All 10 cases pass; full suite (`dotnet test Meezan.Tests`) is green at 73/73 (up from 63 pre-existing).
  - **Conclusion: no bug in `GetLatestAsync` itself** — the resolution algorithm and the Redis→DB degradation are both already correct and are now covered by a permanent regression suite that would fail if either regressed. The originally-reported failure was most likely a data-availability gap (e.g. metal snapshots not yet synced at the time) rather than a logic defect — sub-tasks 2–3 close that gap by making direct pairs for in-use currencies available sooner and by reacting to new wallet currencies immediately, and sub-task 4's manual verification will confirm the live behavior end-to-end.

- Sub-task 2 (2026-08-14): **Live-verified the live Frankfurter contract before coding** (same discipline as Phase 010): `curl "https://api.frankfurter.dev/v2/rates?base=SAR&quotes=EGP,XAU,XAG,USD"` and `base=EGP&quotes=SAR,XAU` both returned all requested quotes — including metals — from a single call with an arbitrary fiat base, confirming the batching strategy is real, not assumed.
  - Added `FrankfurterRateProvider.GetDirectRatesAsync(baseCurrencyCode, quoteCurrencyCodes, ct)` (`Meezan.Services/RateProviders/FrankfurterRateProvider.cs`) — generalizes the existing USD-pivot-only call to an arbitrary base, translating GOLD/SILVER↔XAU/XAG at the same boundary the existing methods use. Frankfurter's rate is always "1 base *native* unit = rate quote *native* units," and a metal's native unit is the troy ounce, not the gram this system stores everything in — so the result is rescaled by `÷31.1034768` when the base is a metal and `×31.1034768` when the quote is a metal (the two cancel out if both are metals, left unchanged). Refactored `ProviderCodeTranslation` (the GOLD→XAU/SILVER→XAG reverse map) out as a small addition alongside the pre-existing `MetalCodeTranslation`.
  - Added `IWalletRepository.GetDistinctActiveCurrencyCodesAsync()` (excludes soft-deleted wallets) and `IAccountRepository.GetDistinctBaseCurrencyCodesAsync()` (excludes soft-deleted accounts) — both single distinct-select queries, no new indexes needed at this scale.
  - `RateService.SyncAsync` now also calls a new private `FetchDirectPairsForInUseCurrenciesAsync`: unions account base currencies and wallet currencies, filters to non-USD *fiat* codes (a GOLD/SILVER wallet's own direct pairs arrive for free as a **quote** under every fiat base's call, so metals are never iterated as a base themselves — no wasted calls), and issues exactly one `GetDirectRatesAsync` call per in-use fiat currency with every other in-use fiat currency plus `GOLD`/`SILVER` as quotes. Results are appended to the same `quotes` list the pre-existing USD-anchored fetch already builds, so they ride the same append-only transaction and the same post-commit Redis refresh loop with no duplicated persistence/cache code.
  - Added `RateServiceInUseCurrencySyncTests.cs` (3 cases): a SAR-base account with a GOLD wallet produces direct `SAR→GOLD`/`SAR→SILVER` snapshots from one batched call (the exact reported scenario); two accounts (SAR-base, EGP-base) produce direct `SAR→EGP`/`EGP→SAR` snapshots from two batched calls; no accounts/wallets at all makes zero `/rates` calls (only the pre-existing `/currencies` call). **Caught a real test bug, not a product bug, while writing the second case**: assumed the two accounts' base currencies would be iterated in insertion order, but SQLite's `Distinct()` (no `ORDER BY`) doesn't guarantee that — a debug run showed `EGP` iterated before `SAR`, which under my original FIFO-queued responses silently cross-assigned each account's canned response to the *other* account's call (each request still got *a* response, just the wrong one), producing wrong-but-plausible-looking rows (`EGP→EGP`, `SAR→SAR`) instead of a hard failure. Fixed by routing both canned responses on the request's actual `base=` query value instead of call order. `dotnet test Meezan.Tests` is green at 76/76 (up from 73).

- Sub-task 3 (2026-08-14): **Discovered an architectural boundary before writing code**: `Meezan.Services` (where `WalletService` lives) has no `PackageReference` to Hangfire at all — only the `Meezan` host project does (confirmed via `grep` across both `.csproj` files). `IJobService`/`JobService` are deliberately Hangfire-agnostic; only `Program.cs` (in `Meezan`) actually calls `BackgroundJob.Enqueue<IJobService>(...)`. Injecting `IBackgroundJobClient` straight into `WalletService` would have crossed that boundary for the first time, so instead added a small anti-corruption adapter mirroring `IRateProvider`'s role for Frankfurter/GoldApi:
  - `IJobEnqueuer` (`Meezan.IServices/IJob/IJobEnqueuer.cs`) — one method, `EnqueueRateSync()`, no Hangfire types in its signature.
  - `HangfireJobEnqueuer` (`Meezan/Jobs/HangfireJobEnqueuer.cs`) — the real implementation, `IBackgroundJobClient.Enqueue<IJobService>(js => js.SyncRates())`, registered `AddScoped<IJobEnqueuer, HangfireJobEnqueuer>()` in `Program.cs` right after the existing Hangfire registration.
  - `WalletService` now takes `IRateService`/`IJobEnqueuer` in its constructor. `Add(...)`: after building the new `Wallet` entity but before committing, checks `RateService.HasRecentSnapshotAsync(request.CurrencyCode, ct)` (a plain DB read, no provider call); commits; and only *after* a successful commit calls `JobEnqueuer.EnqueueRateSync()` if no recent snapshot existed — so a failed commit never schedules a pointless sync, and the sync is enqueued (not awaited), so the request completes immediately either way, satisfying BR-19.
  - Added `IRateService.HasRecentSnapshotAsync(currencyCode, ct)` (reuses the existing `CacheTtl` 48h constant as the freshness bar — the same "how stale is too stale" window the Redis safety-net TTL already encodes) and `IRateSnapshotRepository.HasSnapshotSinceAsync(currencyCode, cutoff, ct)` (any non-deleted snapshot with this currency on *either* side, fetched on or after cutoff).
  - Scope note: only `WalletService.Add` triggers this — `Update`'s currency-change path was left untouched, since the reported requirement was specifically about *adding* a wallet.
  - Added `FakeJobEnqueuer` (records call count) and extended `FakeRateService` with `MarkRecentSnapshot`/`HasRecentSnapshotAsync` (defaults to "no recent snapshot" unless explicitly marked, so tests opt in rather than opt out). New `WalletServiceRateSyncTriggerTests.cs` (2 cases): adding a wallet in an unmarked currency enqueues exactly once; adding one in a currency marked as recently-synced enqueues zero times. `dotnet test Meezan.Tests` is green at 78/78 (up from 76). `dotnet build` verified clean on both `Meezan.Tests.csproj` and `Meezan.csproj` directly (the full `Meezan.sln` build is blocked by IIS Express/Visual Studio holding file locks on `Meezan`'s output in this dev environment — building the two relevant projects individually confirms no compile errors without needing to touch that lock).

- Sub-task 4 (2026-08-14): live-verified against the real app, real SQL Server dev DB, real Frankfurter API, and (partially) real Redis — not just the SQLite/fake-double suite. User approved driving the app myself (`dotnet run` in the background) and handling everything except the actual Redis stop/start, which needed their WSL sudo.
  - **RatesUnavailableException trigger surface**: re-confirmed by code + sub-task-1 tests — only fires when `GetLatestAsync` exhausts direct, inverse, *and* both cross-through-USD legs; `ErrorHandlingMiddleware` maps it to 503, never 500, and `UnitOfWork.ExecuteInTransactionAsync`'s catch-and-rethrow preserves the exception type unchanged through any transactional call site (e.g. `ZakatEngine.ReevaluateAsync`).
  - **Redis-outage path**: attempted live via WSL (`sudo systemctl stop redis-server`), but Redis kept responding to `PING`/`Test-NetConnection` afterward — the user opted to skip re-attempting and rely on sub-task 1's `ThrowingDistributedCache` regression tests instead, which exercise the identical code path (`TryCacheGetAsync`/`TryCacheSetAsync` catching *any* exception and falling through to the DB) with a double that fails every call, not a real outage. Documented here rather than silently treated as fully live-verified.
  - **Enhancement, live**: registered a throwaway user, created an account with `BaseCurrencyCode=SAR`, added a `SAR` wallet, added a transaction — `ZakatEngine.ReevaluateAsync` (fired on every transaction add, regardless of which wallet) needed `SAR→GOLD` to convert that wallet's balance to gold-grams, and it resolved successfully (200 OK). Queried the dev DB directly: before the app restarted with this session's code, only USD-anchored pairs existed (`SELECT DISTINCT FromCurrencyCode,ToCurrencyCode` showed none for `SAR→GOLD`); after restart, the fresh startup sync's log showed the new `SELECT DISTINCT BaseCurrencyCode`/`CurrencyCode` queries firing and a real direct-pair MERGE landing `SAR→GOLD=.001897`/`SAR→SILVER=.127524` — matching this session's hand-derived unit conversion exactly.
  - **New-wallet-currency trigger, live — and a real bug found and fixed**: manually seeded a fictitious `ZZT` currency (Type=Fiat, zero snapshots) via SQL to simulate a genuinely-new currency with no data at all, then added a wallet in it through the real HTTP API. Response returned in 161ms (200 OK) — far too fast to have made a live provider call, and a Hangfire `SyncRates` job (Id 79) was confirmed via direct query against `[HangfireOperation].[HangFire].[Job]` to have been created at the exact moment of the request, proving `WalletService.Add` → `IJobEnqueuer.EnqueueRateSync()` → `HangfireJobEnqueuer` → real `IBackgroundJobClient.Enqueue<IJobService>(SyncRates)` genuinely fires end-to-end.
    - That job then **failed repeatedly** with `HttpRequestException: 422 (Unprocessable Entity)` — Frankfurter rejecting `ZZT` as an unrecognized currency when used as a `base=` in the new direct-pairs call. Because `FetchDirectPairsForInUseCurrenciesAsync` had no per-currency error handling, this exception propagated out of `SyncAsync` *before* its persistence transaction, meaning the run's already-fetched USD-anchored quotes for every *other* currency were silently dropped too on every attempt — a real, live-reproduced regression from sub-task 2, not a hypothetical. **Fixed**: wrapped the per-base `Frankfurter.GetDirectRatesAsync` call in a try/catch that logs a warning and skips just that currency, so one bad/unsupported in-use currency can no longer take down the whole sync (`RateService.cs`). Added `SyncAsync_SkipsAFailingInUseCurrency_WithoutFailingTheEntireRun` to `RateServiceInUseCurrencySyncTests.cs`, simulating the exact live failure (one base returns 422) and asserting the other currency's pair *and* the pre-existing USD-anchored set still persist. Removed the `ZZT` test artifact (wallet + currency row) from the dev DB afterward.
    - Re-ran the live app with the fix: the same job (plus a fresh startup-triggered one) initially still failed a few more times with the identical `422` from the *pre-existing, unmodified* `GetFiatRatesAsync` USD-anchored batch call (not my new code) — traced to `RateService.cs:87`, the original Phase 010 call that fetches all ~163 non-USD fiat currencies as `quotes` in one URL. Investigated whether this was a URL-length/malformed-code issue (it wasn't — reproduced the exact same 163-currency batch by hand against the live API and got a clean 200) and concluded it was very likely transient upstream flakiness/throttling from hitting the free Frankfurter API dozens of times in quick succession during this session's testing, not a code defect. Confirmed by simply letting Hangfire's existing retry policy run its course: both jobs (79 and the startup-triggered one, 80) reached `Succeeded` a few retries later with no code changes, and fresh `RateSnapshot` rows landed (`MAX(FetchedAt)` advanced, row count 9494→9828). **Flagging, not fixing**: the pre-existing single-URL-for-all-fiat-currencies design in `GetFiatRatesAsync` is a latent all-or-nothing fragility point (if it ever *does* fail for a real reason, every currency's USD-anchored refresh is skipped for that run) — out of scope for this task (it predates sub-tasks 1–3 and isn't part of the reported bug or the requested enhancement), but worth a future look if sync failures recur.
  - Cleaned up all throwaway live-test artifacts: test user/account/wallets/transactions (deleted via SQL), the `ZZT` currency/wallet, and stopped the ad-hoc `dotnet run` instance started for this verification. `dotnet test Meezan.Tests` green at 79/79 (added 1 more test this sub-task).
- **Phase 016 complete.** Diagnosed and confirmed the direct/inverse/cross-through-USD resolution and Redis→DB fallback were already correct (added permanent regression coverage); extended the sync job to fetch direct pairs for every currency actually in use; wired a background-job trigger for brand-new wallet currencies via a Hangfire-agnostic adapter; and, through live verification against the real app/DB/API, found and fixed a genuine resilience gap the enhancement had introduced (one bad in-use currency could silently break the whole sync run) before it could reach production.
